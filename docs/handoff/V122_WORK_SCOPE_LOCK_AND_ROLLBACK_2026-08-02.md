# v1.2.2 작업 범위 잠금 및 잘못 진행된 작업 복구 기록

작성일: 2026-08-02
대상 버전: `1.2.2`
현재 브랜치: `codex/v122-ui-simplification`
기준 원격: `origin/codex/v122-ui-simplification`

## 1. 왜 작업이 꼬였는가

1. Luna 실행 계획의 정식 순서는 `F0 → V1 → V2 → V3 → V4 → A0 → A1 → C1 → V5 → V6 → A2 → A3 → A4 → A5 → Q1 → I1 → I2 → R1`이다.
2. 현재 작업 로그는 V1~V4의 이 계획상 완료 기록을 닫지 않은 채 A0·A1·C1·V5를 먼저 진행했다. 이전 구조 벽·도로 핸드오프가 존재한다는 사실을 Luna 계획의 V1~V4 완료 승인으로 잘못 취급했다.
3. `"순서대로 진행해"`를 다음 모든 페이즈를 자동 실행해도 된다는 포괄 승인으로 해석했다. 실제 계획은 한 패킷씩 입력·허용 파일·완료 게이트를 확인하도록 요구한다.
4. 계획은 직전 기능 SHA와 종료 문서가 커밋되거나 사용자가 정확한 diff를 승인하기 전에는 다음 패킷을 시작하지 못하게 한다. 그러나 현재는 미커밋 A1/C1/V5 변경이 섞인 작업 트리에서 다음 상태를 보고했다.
5. 그 결과 “계획표에 적힌 순서”, “이전 시각 작업의 실제 상태”, “이번 패킷의 허용 범위”가 한 작업 트리에 섞였다. 이것이 임의 진행과 복구 대상이 불명확해진 직접 원인이다.

## 2. 앞으로의 작업 범위 잠금

- 사용자가 명시한 현재 페이즈·하위 패킷 하나만 수행한다. `그래`, `진행해`, `순서대로`는 다음 페이즈 전체 실행 승인으로 해석하지 않는다.
- 구현 전에 반드시 다음 네 항목을 보고하고 승인을 받은 뒤 시작한다: 현재 페이즈, 변경 허용 파일 목록, 직접 실행할 테스트, 완료 게이트.
- 미해결 게이트가 하나라도 있으면 다음 페이즈로 넘어가지 않는다. 특히 실제 `1280×720` 화면·청취·사용자 승인이 필요한 항목은 자동 테스트 PASS만으로 닫지 않는다.
- V1~V4 상태가 문서로 닫히기 전에는 A0 이후 페이즈를 새로 시작하지 않는다. V5 자동 gate가 PASS여도 실제 화면 비교 전에는 V6을 시작하지 않는다.
- 새 패킷은 승인된 기준 SHA에서 시작한다. 작업 트리가 혼합 상태이거나 직전 기능 SHA가 미커밋이면 새 구현을 시작하지 않고 변경 목록만 보고한다.
- 커밋·푸시·빌드·Full 검증·태그·Release는 해당 작업을 사용자가 별도로 지시한 경우에만 수행한다.
- 이전 사용자 변경은 `git reset --hard`, 광범위한 `git restore`, 무차별 삭제로 되돌리지 않는다. 복구는 파일 목록 또는 커밋 범위를 먼저 확정한 뒤, 명시된 대상만 수행한다.

## 3. 현재 복구 후보와 보존 원칙

현재 작업 트리에는 다음이 섞여 있다.

- 커밋된 변경: `f9a912b` 전투 타깃 우선순위 수정, `efab13e` 도로·구조 벽 통합
- 미커밋 release-polish 변경: A0·A1-A~E·C1·V5 코드, 데이터, 테스트, QA·핸드오프 문서
- 별도 기존 변경: Update 4 `.import` 6개와 자동 생성 `.gd.uid` 파일 등

복구는 선택하지 않았다. 미커밋 release-polish 변경, 커밋된 두 수정, 별도 기존 변경을 모두 보존한 채 기준선을 다시 판정한다. 따라서 이 문서는 삭제 목록이 아니라 이후 작업을 잠그는 범위·원인·재시작 기록으로 사용한다.

## 4. 사용자 결정과 순서 재시작

사용자는 복구하지 않고 계획의 맨 처음부터 다시 진행하며, 꼬인 부분은 진행 중 분리·수정하기로 결정했다. 따라서 기존 A0·A1·C1·V5 변경은 보존하되 승인된 완료로 간주하지 않는다. 이후 모든 판정은 F0 기준선을 다시 읽은 뒤 새로 기록한다.

### F0 재검증에서 확인된 혼선

- F0-V 정적 inventory는 활성 44개·고유 경로 37개·`PASS 19 / NEEDS_NORMALIZATION 25 / DISCONNECTED 0`·비행 불일치 2개로 파일 존재 검사를 통과했다.
- F0-V의 실제 `1280×720` 캡처는 현재 headless dummy renderer에서 viewport texture가 비어 실패했다. 기존 캡처 파일을 현재 런타임의 승인 증거로 재사용하지 않는다.
- F0-A 원본 기록은 76개·실제 런타임 54개·data-only 12개·unconnected 10개였지만, 현재 혼합 작업 트리에서 inventory를 재생성하자 `actual_runtime 53 / data_only 23 / unconnected 0`으로 달라졌다. A1 변경이 F0 기준선의 정적 연결 판정을 바꾼 증거다.
- F0-R은 Q1 공백 5개를 유지하지만, 계획상 F0 다음은 Q1이 아니라 V1이다. 기존 F0-R 문서의 “다음 Q1” 문구는 잘못된 연결로 확인했다.

## 5. 재시작 절차

1. F0-V·F0-A·F0-R의 현재 파일·기계 목록·문서를 기준선으로 재분류한다.
2. F0 결과와 작업 트리의 차이를 별도 기록하고, 기존 구현을 삭제하지 않는다.
3. `V1-A`부터 계획 순서대로 한 패킷씩 진행한다. 각 패킷은 허용 파일·테스트·완료 게이트를 먼저 기록한다.
4. 공통 구조 결함이나 기준선 변경을 발견하면 다음 패킷으로 넘어가지 않고 현재 패킷을 정정한다.
5. 각 패킷 뒤 `git diff --check`, 최소 관련 테스트, 핸드오프와 `CURRENT.md`를 갱신한다.
6. 사용자 지시가 없는 한 다음 페이즈·빌드·커밋·푸시·Full 검증을 자동 실행하지 않는다.
