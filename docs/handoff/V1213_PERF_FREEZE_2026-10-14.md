## 2. 요청·측정 방법

사용자 원문: “지금 마왕성 게임을 실제로 켜서 테스트해볼 때 컴퓨터가 거의 멈추다시피 한다. 기존엔 안 그랬는데 갑자기 이렇게 됐다. 원인 파악해서 수정해라.”

- 동일 PC: i5-13500, 논리 CPU 20개, RTX 3060 Ti, Godot `4.6.3.stable.official.7d41c59c4`, Windows, Vulkan/Forward+.
- 실제 1920×1080 창과 게임의 `GameRoot.tscn`을 실행한다. Main도 이 동일 씬을 인스턴스화한다. headless 결과로 렌더 FPS를 대체하지 않았다.
- 타이틀 30초 → 실제 새 게임·이름 입력·오프닝 진행 → DAY1 관리 60초(마우스, 중간 버튼 팬, 휠 줌) → 전투 화면 누적 60초 → 결과 10초. DAY1은 자연 종료가 빨라 동일 DAY1 전투를 재시작해 실제 전투 60초를 모았다. 모든 버전에서 동일 절차, AI/오디오/물리 처리를 유지한다. 60초 뒤 결과 화면 진입은 종료 fixture로 구분한다.
- 추가: DAY2 방 튜토리얼 팬 15초, 건설 위치 탐색 10초, 비활성 타이틀 15초. 마우스는 실제 GUI viewport의 입력 경로에 약 60회/초로 전달하며 물리 마우스의 1,000/8,000 Hz 스트레스는 아니다.
- 각 구간 FPS, 실제 프레임 간격 평균/p95/최댓값, 엔진 처리·물리 시간, GUI 프로세스 CPU/RAM/private memory, 전체 GPU 사용률/메모리/전력, 프로세스 수, 노드·오브젝트·고아 노드·draw call, VSync/상한/엔진 및 Windows 포커스를 1초 단위로 저장했다.
- CPU는 **전체 20개 논리 CPU 대비 %**다. GPU는 nvidia-smi의 **GPU 전체 값**으로 다른 앱의 사용을 포함하며 Godot 전용 %가 아니다. CSV는 엔진/OS 샘플을 최근접 타임스탬프로 결합한다. 전환 직후의 FPS 갱신 지연 때문에 요약은 기본 첫2초, 실제 포커스 전환과 cold placement fixture는 첫4초를 제외한다.
- 수동 `Time.get_ticks_usec()` 계측은 폐기 가능한 `tmp/v1213_perf/` 복사본에만 삽입했다. 제품 코드에는 계측/print/autoload를 추가하지 않았다. 재귀 함수 시간은 중첩을 포함하므로 부모와 자식 시간을 합산해 총 CPU 시간으로 해석하지 않는다.
- 개인 세이브를 사용하지 않고 각 실행마다 별도 APPDATA를 쓴다. 제품의 저장 플래그를 비활성화했다. 생성 로그/PNG/CSV/캐시는 tmp에만 둔다.

## 3. 확정한 원인·수정

### 무제한 렌더링

현재판의 VSync 해제 실험에서 활성 타이틀 평균 **4,200.2 FPS / GPU 86.5% / CPU 4.18%**, 비활성 타이틀 **4,274.5 FPS / GPU 86.4% / CPU 4.07%**를 측정했다. 약 180~190 W 구간을 실제 기록했다. 같은 실행에서 120 FPS 상한만 넣으면 GPU **24.8% / CPU 0.57%**, 30 FPS이면 **14.0% / CPU 0.23%**로 낮아졌다. 초당 수천 번 그리는 경로와 상한의 효과는 측정으로 확인했다.

- `project.godot`: `application/run/max_fps=120`, 기본 VSync Enabled를 명시.
- `UISettings`: 실제 창의 focus_exited에서 렌더 상한 30, focus_entered에서 실행 시의 상한 복원. 기존 상한이 30보다 낮으면 높이지 않는다. headless에는 창 포커스 정책을 적용하지 않는다.
- 물리 tick rate, Engine.time_scale, AI·전투·대화·오디오 타이머는 바꾸지 않는다.
- `low_processor_mode`는 추가하지 않았다. 타이틀뿐 아니라 전투·튜토리얼 애니메이션까지 있는 게임 전체의 갱신 방식을 바꾸는 대신 측정된 무제한 렌더링에 상한을 적용했다. [Godot FPS 상한](https://docs.godotengine.org/en/4.6/classes/class_projectsettings.html#class-projectsettings-property-application-run-max-fps), [유휴 모드 설명](https://docs.godotengine.org/en/4.6/classes/class_projectsettings.html#class-projectsettings-property-application-run-low-processor-mode).

### 튜토리얼 재생성

팬/줌에서 `_tutorial_build_overlay()`를 호출하는 신규 경로는 DAY1의 고정 HUD 대상을 가리킬 때도 패널·폰트 맞춤·반복 Tween을 다시 만들었다. 초기 현재판 관리에서 팬 구간은 약 50 ms/초, 별도 방 팬 구간은 약 63 ms/초의 overlay 생성 비용이었다. 이것만으로 PC 전체 멈춤을 설명하지 않는다.

- `GameRoot`: 기존 overlay에 화면·단계·step·focus/message rect·문구·언어·글자 배율·터치 모드·안내 수준·행동 모드의 표시 상태를 저장한다. 동일하면 기존 노드와 Tween을 재사용한다.
- 방 focus가 팬/줌으로 움직이거나 문구/언어/단계가 바뀌면 기존 생성 경로를 유지한다. 비활성/미표시 단계에서는 overlay를 제거한다. HUD가 재구성되면 overlay도 없어지므로 이전 화면 캐시를 재사용하지 않는다.
- 건설 규칙/hit-test, `_evaluate_facility_placement`, 라벨 높이·최소 글자, 툴팁, stretch aspect, hud.clear 호출 정책은 바꾸지 않았다.

## 5. 다른 의심 경로·환경 분리

- `_tutorial_badge_overlaps_management_ui`: 이동하는 방 튜토리얼에서 UI 재귀 탐색은 유지한다. 고정 overlay 재사용 시 탐색·라벨 fitting 자체를 생략한다. 재귀의 중첩 시간과 root overlay 전체 시간을 구분한다.
- `BuildingPlacementController.target_room`, `_evaluate_facility_placement`, `_management_label_layout`: 실제 건설 탐색과 draw 경로를 계측했다. 표시/규칙을 깨뜨릴 수 있는 별도 캐시는 넣지 않았다.
- `_fit_label_to_bounds`/rich label: 화면 생성·실제 overlay 변경 때만 작업이 나타난다. dcd5743의 최소 높이와 ReadableTooltipButton의 툴팁 기준을 유지한다. tooltip은 요청 시 생성하는 함수이며 기본 매 프레임 재배치 경로가 아니다.
- `hud.clear`/`_set_screen`: 화면 전환 때만 호출되는 기록을 유지한다. 정상 idle·팬·건설 단계의 연속 HUD clear 폭주는 없었다.
