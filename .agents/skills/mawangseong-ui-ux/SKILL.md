# 마왕성 UI·UX

이 스킬은 공개 범용 코어 **Game UI/UX Rules v1.0.0**을 마왕성에 적용하는 프로젝트 계층이다.

- 코어 저장소: `https://github.com/bluehige/study`
- 범용 디렉터: `skills/game-ui-ux-director`
- 프로젝트 스킬 생성 원칙: `skills/game-ui-ux-project-builder`

범용 교과서를 반복하지 않고, 마왕성의 화면·게임 루프·Godot 구조·검수 게이트만 고정한다.

## 1. 작업 전 필수 확인

반드시 다음 순서로 읽는다.

1. `AGENTS.md`
2. `docs/handoff/CURRENT.md`
3. 대상 버전의 최신 UI handoff
4. 대상 화면의 scene, script, theme, controller
5. 관련 테스트와 캡처 도구
6. 현재 브랜치, 기준 SHA, 변경 허용 범위

`docs/handoff/CURRENT.md`가 기록한 현재 게이트와 과거 문서가 충돌하면 CURRENT와 최신 사용자 결정이 우선한다. 특정 SHA와 빌드 hash는 영구 디자인 규칙이 아니라 해당 검수 후보의 증거 식별자다.

## 2. 제품 경험 우선순위

현재 최우선 제품 목표:

1. 게임 진행이 간단할 것
2. 건물과 몬스터 배치로 승리하는 재미를 줄 것
3. 전투의 밸런스가 맞을 것

UI는 위 목표를 대신 달성했다고 선언할 수 없다. UI가 해야 할 일은 다음이다.

- 현재 진행 단계와 다음 행동을 명확히 한다.
- 배치 선택과 전투 결과의 인과를 읽을 수 있게 한다.
- 전투 중 위협·방어선·명령 대상·결과를 가리지 않고 보여준다.
- 결과 화면에서 패배 원인과 다음 배치 수정점을 이해하게 한다.
- 자동 검사와 실제 사용자 판단을 분리한다.

## 3. 현재 기준 흐름

제품 2.0 DAY 1~5 검증 흐름은 다음 다섯 상태를 사용한다.

```text
침입 확인 → 배치 → 방어 시작/countdown → 전투 → 결과
```

타이틀은 이 흐름의 진입점이다. 게임 기획에 없는 별도 관리 단계, 방별 설정 모드, 중복 확인 화면을 임의로 추가하지 않는다.

## 4. 필수 작업 절차

### A. 조사

- 실제 데이터 출처와 화면 상태를 확인한다.
- 기존 사용자 피드백과 현재 검수 증거를 읽는다.
- 기능·밸런스 문제와 UI 표시 문제를 분리한다.

### B. 화면 계약

`references/screen-contracts.md`에서 대상 화면 계약을 읽고, 변경이 필요하면 먼저 계약을 수정한다. 계약 없이 이미지 목업이나 Godot 노드부터 만들지 않는다.

### C. 정보 계층

정보를 다음으로 분류한다.

- `P0`: 지금 판단과 진행에 계속 필요
- `P1`: 선택·위협·오류 상태에서만 필요
- `P2`: 요청하거나 포커스했을 때 필요
- `P3`: 로그·도감·사후 기록

P2·P3 정보를 상시 패널로 노출해 지도나 전장을 가리지 않는다.

### D. 시각 설계

`references/design-system.md`의 현재 baseline을 사용하되, 값을 기계적으로 보존하지 않는다. 기능 역할과 실제 화면 가독성을 기준으로 수정한다.

- 중요도가 높은 요소가 크기·대비·위치에서 우선돼야 한다.
- 장식이 버튼처럼 보이거나 버튼이 장식처럼 묻히면 실패다.
- 마왕성의 어두운 판타지 톤은 유지하되, 검은 패널로 배경과 전장을 덮지 않는다.
- 금색은 주 행동과 핵심 강조에 제한하고 모든 테두리에 남용하지 않는다.
- 위험·경로·성공·선택은 색상 외 형태·문구·아이콘을 함께 사용한다.

### E. 구현

`references/godot-implementation.md`를 따른다.

- 기존 theme/token과 controller 책임을 재사용한다.
- UI 작업에 밸런스, AI, spawn, HP/ATK, 시설·몬스터 효과 변경을 섞지 않는다.
- 변경이 게임 규칙을 요구하면 UI PR과 분리해 제품 계약 승인을 받는다.
- 지원 입력과 해상도에서 focus, hit rect, text overflow, overlay blocking을 검사한다.

### F. 검증

`references/validation-matrix.md`를 따른다.

- 관련 자동 테스트
- 필요한 해상도의 실제 Godot 렌더
- 실제 입력 흐름
- 요청되거나 승인 게이트에서 요구되는 사용자 테스트

자동 assertion, 화면 비겹침, 콘솔 오류 0건만으로 `직관적`, `재미있음`, `V20_UI_OWNER_ACCEPTED`를 선언하지 않는다.

## 5. 마왕성 Hygiene Gate

다음 중 하나라도 재현되면 총점과 관계없이 `FAIL`이다.

- 타이틀·침입·배치·전투·결과 흐름의 다음 행동을 실행할 수 없음
- 침입 방향, 고정 경로, 배치 가능 위치 또는 시작 차단 이유를 알 수 없음
- 카드와 슬롯의 실제 drag/drop 판정이 보이는 강조와 다름
- 배치가 저장·전투 spawn·결과에 반영된다는 피드백이 끊김
- 전투 HUD가 몬스터·적·현재 교전 구역을 지속적으로 가림
- 전술 명령의 대상·비용·사용 가능 여부·실패 이유가 보이지 않음
- 결과 화면에서 승패 원인과 다음 행동을 구분할 수 없음
- 키보드 포커스 또는 마우스 입력이 숨은 패널·텍스트 입력·overlay에 가로막힘
- 필수 정보가 색상 하나로만 표현됨
- 실제 게임 데이터와 UI 문구가 불일치함

확인하지 못한 항목은 PASS가 아니라 `UNKNOWN`으로 둔다.

## 6. 화면별 불변 원칙

### 타이틀

- 저장이 없으면 새 시작이 유일한 주 행동이다.
- 유효 저장이 있을 때만 이어하기를 보여준다.
- 개발·검수 badge는 제품 위계와 분리한다.

### 침입 확인

- 적 대표, 적 목표, 고정 침입 순서, DAY 주의점을 한 맥락에서 읽는다.
- 배치 전 플레이어가 답해야 할 전략 질문을 분명히 한다.
- 주 행동은 배치 시작이다.

### 배치

- 중앙 고정 지도와 실제 침입 경로를 유지한다.
- 방 선택 때문에 지도가 이동·축소·교체되지 않는다.
- 시설·몬스터 카드, 유효·비유효 대상, 배치 상태, Undo, 시작 가능 여부를 연결한다.
- invalid drop은 상태를 바꾸지 않고 이유와 가능한 다음 행동을 알려준다.
- 방어 시작은 배치 완료 후의 주 행동이다.

### countdown

- 배치가 확정됐음을 보여주고 취소 가능 시간과 행동을 명확히 한다.
- 중복 확인 대화상자를 추가하지 않는다.

### 전투

- 전장이 최우선이다.
- 상단 목표·왕좌 HP, 한 줄 방어선 진행, 조건부 위협, 작은 속도 제어를 사용한다.
- 네 전술 명령은 이름·비용·사용 가능 여부를 기본으로, 선택 중에는 대상·효과·취소를 보여준다.
- 성공과 실패는 실제 대상, 자원 변화, 지속·완료 또는 실패 이유로 피드백한다.

### 결과

- 승패, 핵심 원인, 잘한 점, 다음 변경점, 핵심 지표를 우선한다.
- 상세 전투 기록은 기본 접힘이다.
- 패배 시 `배치 수정`이 주 행동, 같은 배치 재도전은 보조 행동이다.
- 결과를 근거 없이 새로 계산하지 않고 제품의 evidence/정산 데이터를 표시한다.

## 7. 검수 판정

범용 GUX-Q8과 E0~E4를 사용한다.

- 구조적 PASS: blocker 0, 총점 80 이상, 모든 차원 3 이상
- 사용자 UX 승인: 동일 source/build의 E4 증거와 명시적 사용자 판정 필요
- 현재 후보의 과거 PASS는 해당 source SHA에만 유효하다.
- 기능·데이터·자산·입력 변경으로 source/build가 달라지면 영향 범위를 재검증한다.

현재 제품 2.0의 사용자 승인 게이트는 최신 handoff의 정확한 문구와 SHA/hash를 다시 읽는다. 스킬 문서에 적힌 과거 값만 보고 승인 처리하지 않는다.

## 8. 출력 형식

마왕성 UI·UX 보고서는 다음 순서로 작성한다.

1. 판정과 증거 수준
2. 기준 브랜치·SHA·빌드·해상도·입력
3. 플레이어 질문과 핵심 결정
4. Hygiene blocker / UNKNOWN
5. GUX-Q8 차원별 점수와 근거
6. 화면별 정보 계층과 문제
7. 시각 디자인 방향
8. 구현 파일과 비변경 범위
9. 관련 검증과 사용자 테스트
10. 다음 PR 단위와 승인 게이트

모든 지적에는 `저장소·화면 근거 → 플레이 영향 → 수정 규칙 → 재검증`을 포함한다.

## 9. 금지

- 사용자가 요청하지 않은 전체 UI 재작성
- 승인된 제품 흐름을 새 화면과 버튼으로 확장
- UI 수정에 밸런스·콘텐츠 변경 혼합
- 정적 이미지 한 장으로 최종 UX 승인
- 자동 테스트 통과를 재미·직관성·출시 적합 판정으로 확대
- 기존 작업 브랜치, 태그, Release, 저장 파일 변경
- `release/v2.0` 실험선을 제품 출시선에 통째로 병합
